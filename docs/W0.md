# W0 — Write-Baseline: ein HTTP-Request pro Zeile

> **Track:** Write (Client → Server → DB)
> **Ziel:** Die absichtlich schlechteste sinnvolle Implementierung. Sie liefert die
> Referenzzahl, gegen die alle folgenden Write-Stufen (W1–W8) antreten.

## Konzept

Der Client möchte *N* Zeilen in die Datenbank schreiben. In dieser Stufe tut er das
auf die naheliegendste, aber ineffizienteste Weise:

1. Für **jede einzelne Zeile** wird ein **eigener HTTP-Request** abgesetzt.
2. Der Server nimmt genau eine Zeile entgegen und speichert sie mit
   `repository.save(...)`.
3. Es gibt **keine explizite Transaktionsklammer** — jeder `save()`-Aufruf läuft in
   seiner eigenen Transaktion und **committet einzeln**.

Damit summieren sich gleich **drei** Kostenblöcke, jeweils *pro Zeile*:

| Kostenblock | Wo? | Was passiert pro Zeile |
|-------------|-----|------------------------|
| HTTP-Round-Trip | Client ↔ Server | Verbindung, Header, Request/Response |
| INSERT | Server → DB | ein einzelnes SQL-INSERT über den Pool |
| COMMIT | DB | ein eigener Transaktions-Commit (fsync!) |

## Warum ist das langsam?

Der teuerste versteckte Posten ist oft der **Commit**: PostgreSQL muss bei jedem
Commit das Write-Ahead-Log dauerhaft auf die Platte schreiben (`fsync`). Ein Commit
pro Zeile bedeutet einen `fsync` pro Zeile. Dazu kommt der **HTTP-Overhead**: Selbst
über `localhost` kostet jeder Request Zeit für Auf-/Abbau und Header-Verarbeitung —
Zeit, in der *keine* Nutzdaten fließen.

Das Ergebnis: Der Durchsatz wird nicht von der Datenmenge bestimmt, sondern von der
**Anzahl der Round-Trips und Commits**.

## Code-Walkthrough

**Server** — genau eine Zeile speichern:

- `controller/WriteController.java` → `w0SingleRow(...)`: nimmt einen einzelnen
  `MeasurementRequest` per `@RequestBody` entgegen.
- `service/WriteService.java` → `saveOne(...)`: ruft `repository.save(entity)` auf.
  Bewusst **ohne** `@Transactional`, damit jeder Aufruf einzeln committet.

**Client** — die Schleife (`client/src/stages.ts`, Stufe `w0`):

```ts
for (let i = 0; i < count; i++) {
  const resp = await fetch('/api/write/w0', { method: 'POST', body });
  await resp.arrayBuffer();
}
```

Die Zeit wird über die **gesamte Schleife** clientseitig gemessen (Wanduhr), weil es
keine einzelne „Serverzeit" für den ganzen Vorgang gibt.

> **Begrenzung:** W0 ist im Client auf **2000 Zeilen** gedeckelt (`W0_MAX_ROWS`).
> Ein HTTP-Request pro Zeile skaliert so schlecht, dass größere Zahlen den Unterricht
> nur aufhalten. Zum Vergleich zählt ohnehin der **Durchsatz** (Zeilen/s), nicht die
> absolute Zeilenzahl.

## Messung

Im Dashboard oben eine kleine Zeilenzahl wählen (z. B. 2000), dann **W0** ausführen.
Beobachte:

- **Zeilen/s**: sehr niedrig — das ist die Referenz.
- **TTFB**: Zeit bis zur ersten Antwort (hier wenig aussagekräftig, da viele Requests).

Typische Größenordnung auf einem Entwickler-Notebook: **wenige Hundert bis wenige
Tausend Zeilen/s**. Genau diese Zahl macht die späteren Sprünge eindrucksvoll.

## Fallstricke & Trade-offs

- **Nicht** so etwas in Produktion bauen. W0 existiert nur als Lehr-Referenz.
- Der `fsync`-pro-Commit-Effekt ist real, aber hardware-abhängig (SSD vs. HDD, WAL-
  Konfiguration). Deshalb sind **relative** Vergleiche aussagekräftiger als absolute.

## Ausblick

- **W1** behält die Einzel-INSERTs bei, sendet aber **alle Zeilen in einem Request** —
  isoliert damit den reinen HTTP-Overhead.
- **W3** bündelt die INSERTs zum **JDBC-Batch** — der eigentliche große Sprung.
- **W4** fasst alles in **eine Transaktion** — ein Commit statt *N*.
