# R7 — Binärformat (CBOR) statt JSON

> **Track:** Read · **Vorgänger:** [R6](R6.md) · **Nachfolger:** [R8](R8.md)

## Konzept

JSON ist textbasiert und dadurch etwas „geschwätzig": Feldnamen als Text, Zahlen als
Ziffernfolgen, viele Trennzeichen. **CBOR** (Concise Binary Object Representation, RFC 8949)
ist ein **binäres** Format mit demselben Datenmodell wie JSON — nur kompakter und schneller
zu (de)serialisieren.

R7 liefert dieselben Projektionsdaten wie [R1](R1.md), aber als CBOR. Damit der Client das
Binärformat nicht selbst dekodieren muss, kommt die Zeilenzahl im Header `X-Rows`.

## Was die Messung zeigt

100 000 Zeilen (ohne payload):

| Stufe | Nutzlast | Faktor ggü. R1 |
|-------|----------|----------------|
| R1 (JSON) | 10,75 MB | — |
| **R7 (CBOR)** | **8,06 MB** | **~0,75× (≈ 25 % kleiner)** |

CBOR spart hier ~25 %. Wie viel genau, hängt von den Daten ab: Bei vielen wiederholten
**Feldnamen** und kompakten **Zahlen** ist der Gewinn größer; bei langen Freitexten kleiner.

## Code-Walkthrough

- `controller/ReadController.java` → `r7Cbor()`: serialisiert die Projektion mit einem
  `CBORMapper` (Jackson 3, Paket `tools.jackson.dataformat.cbor`) und setzt
  `Content-Type: application/cbor`, `X-Wire-Bytes` und `X-Rows`.
- Client (`stages.ts`, `r7Stage`): misst die Byte-Größe direkt und liest die Zeilenzahl aus
  `X-Rows`.

## Fallstricke & Trade-offs

- **Nicht menschenlesbar:** CBOR lässt sich nicht einfach im Browser/Log ansehen — schlechter
  für Debugging.
- **Client-Support nötig:** Der Empfänger braucht einen CBOR-Decoder. JSON ist universell.
- **Kompression relativiert den Vorteil:** gzip über JSON (siehe [R4](R4.md)) holt oft mehr
  heraus als CBOR unkomprimiert. Am kleinsten wird es mit **CBOR + Kompression**.
- Für maximale Kompaktheit/Schema-Sicherheit sind schemabasierte Formate (Protobuf, Avro)
  noch effizienter — aber aufwändiger (Schema-Pflege, Codegen).
