# R0 — Read-Baseline: die komplette Tabelle als ein JSON-Array

> **Track:** Read (DB → Server → Client)
> **Ziel:** Die absichtlich schlechteste sinnvolle Leseimplementierung. Referenz für
> die Read-Stufen R1–R8.

## Konzept

Der Client möchte Messdaten anzeigen. In dieser Stufe holt der Server sie auf die
naivste Weise:

1. `repository.findAll()` lädt **alle** Zeilen als **vollständige Entities** in eine
   `List` im Server-Speicher.
2. Diese Liste wird **komplett** in **ein großes JSON-Array** serialisiert.
3. Erst wenn das gesamte Array fertig ist, geht die Antwort an den Client.

## Warum ist das schlecht?

Gleich drei Schwächen greifen zusammen:

| Schwäche | Folge | Wird angegriffen von |
|----------|-------|----------------------|
| **Alles auf einmal** in den RAM | Speicher wächst linear mit der Tabelle; bei Millionen Zeilen droht `OutOfMemoryError` | R2 (Pagination), R3 (Streaming) |
| **Vollständige Entities** (alle Spalten inkl. `payload`) | unnötig große Nutzlast, auch wenn der Client nur wenige Felder braucht | R1 (DTO-Projektion) |
| **Erst fertig serialisieren, dann senden** | hohe **Time-To-First-Byte**; der Client sieht lange gar nichts | R3 (Streaming), R8 (Reactive) |

Zusätzlich muss der Client das **gesamte** JSON parsen, bevor er etwas anzeigen kann —
auch das kostet spürbar Zeit und Speicher.

## Code-Walkthrough

**Server:**

- `service/ReadService.java` → `findAllNaive()`: `return repository.findAll();`,
  annotiert mit `@Transactional(readOnly = true)`.
- `controller/ReadController.java` → `r0FindAll()`: gibt die `List<Measurement>`
  **direkt** zurück. Jackson serialisiert die **Entities selbst** — bewusst das
  Anti-Pattern, das R1 mit einem schlanken DTO auflöst.

**Client** (`client/src/stages.ts`, Stufe `r0`):

```ts
const m = await measure('/api/read/r0', { method: 'GET' });
const rows = (JSON.parse(m.bodyText) as unknown[]).length;
```

Das Mess-Harness zählt die **übertragenen Bytes** direkt aus dem Antwort-Stream und
liest die **Serverzeit** aus dem `Server-Timing`-Header.

## Messung

Voraussetzung: vorher **Seed** ausführen (z. B. 100 000 Zeilen). Dann **R0** starten.
Beobachte in der Tabelle:

- **KB / MB**: die volle Nutzlast auf der Leitung — inkl. aller Spalten und `payload`.
- **TTFB ≈ Gesamtzeit**: typisch für „erst alles fertig, dann senden".
- **Server ms**: Zeit zum Laden + Serialisieren im Server.

Merke dir diese Zahlen — R1 (Projektion) senkt zuerst die **Bytes**, R3 (Streaming)
senkt vor allem die **TTFB**.

## Fallstricke & Trade-offs

- R0 **funktioniert** für kleine Tabellen völlig problemlos — genau das macht es
  gefährlich: Es fällt erst bei großem Datenbestand um. Für die Demo daher ruhig mit
  vielen Zeilen (und `payloadLength > 0`) seeden, damit der Effekt sichtbar wird.
- Entities direkt zu serialisieren koppelt zudem die API an das DB-Schema — ein
  Wartungsproblem, das R1 nebenbei mitlöst.

## Ausblick

- **R1** liefert statt der ganzen Entity ein **DTO** mit nur den benötigten Spalten →
  weniger Bytes.
- **R2** holt die Daten **seitenweise** (Keyset) statt alles auf einmal.
- **R3** **streamt** die Zeilen (NDJSON) → niedrige TTFB, konstanter Speicher.
