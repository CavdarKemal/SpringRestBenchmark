# W7 — Parallel-Ingest über Virtual Threads (+ Pool-Sizing)

> **Track:** Write · **Vorgänger:** [W6](W6.md) · **Nachfolger:** [W8](W8.md)

## Konzept

Alle bisherigen Stufen arbeiten **seriell** — ein Thread, eine Verbindung. W7 verteilt den
Ingest auf **mehrere Verbindungen gleichzeitig**: Die Zeilen werden in Partitionen
aufgeteilt, jede Partition läuft als eigener Task (JDBC-Batch mit
`reWriteBatchedInserts=true`), und alle Tasks laufen **parallel** auf einem
**Virtual-Thread-pro-Task-Executor**.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (var part : partitions) futures.add(executor.submit(() -> batchInsert(part)));
    ...
}
```

**Virtual Threads** (Java 21) machen Nebenläufigkeit billig: Man kann bedenkenlos viele
Tasks starten, ohne einen knappen Plattform-Thread-Pool zu erschöpfen.

## Die eigentliche Lektion: Pool-Größe ↔ Parallelität

Parallelität hilft nur, wenn die Datenbank **genug Verbindungen** bereitstellt. Deshalb
nutzt W7 einen **eigenen HikariCP-Pool mit 16 Verbindungen** (≥ Parallelitätsgrad 8). Mit
dem Standard-Pool (10) oder gar einem kleinen Pool würden die Tasks um Verbindungen
konkurrieren und sich **serialisieren** — der Parallelitätsvorteil verpufft.

> Genau hier wird das Connection-Pool-Sizing, das in einer seriellen Welt (W2–W6) kaum eine
> Rolle spielt, zum entscheidenden Faktor.

## Was die Messung zeigt

| Stufe | Zeilen | Server ms | Zeilen/s |
|-------|--------|-----------|----------|
| W4 (seriell, Batch+reWrite) | 100000 | ~2250 | ~44 000 |
| **W7 (parallel, VThreads)** | 100000 | ~1190 | **~84 000** |
| W6 (COPY, seriell) | 100000 | ~975 | ~102 000 |

W7 verdoppelt gegenüber dem seriellen W4 grob den Durchsatz. Ob COPY (W6) noch überholt
wird, hängt stark von Kernen, Platte und WAL-Konfiguration ab — auf write-lastigen Systemen
ist COPY oft schwer zu schlagen, aber W7 kommt nah heran.

## Fallstricke & Trade-offs

- **Pool zu klein → kein Nutzen.** Der wichtigste Stolperstein; deshalb der dedizierte Pool.
- Mehr Parallelität ist nicht beliebig gut: Zu viele gleichzeitige Schreiber erzeugen
  **Contention** (Locks, WAL, I/O). Der optimale Grad ist ein Tuning-Thema.
- Reihenfolge/Transaktionalität über Partitionen hinweg geht verloren (jede Partition
  committet für sich) — für reinen Bulk-Insert akzeptabel.

## Ausblick

- **[W8](W8.md)** wechselt das Programmiermodell komplett: **reaktiv/non-blocking** über
  R2DBC — und zeigt, dass „reaktiv" nicht automatisch „schneller beim Bulk-Insert" heißt.
