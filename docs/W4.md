# W4 — JDBC-Batch mit `reWriteBatchedInserts=true`

> **Track:** Write · **Vorgänger:** [W3](W3.md) · **Nachfolger:** [W5](W5.md)

## Konzept

W4 ändert gegenüber W3 **nur eine Verbindungseinstellung**: den pgjdbc-Parameter
`reWriteBatchedInserts=true`. Damit erkennt der Treiber, dass ein Batch aus lauter
gleichartigen INSERTs besteht, und **schreibt ihn in ein Multi-Row-INSERT um**:

```sql
-- statt 1000× "INSERT INTO measurements (...) VALUES (?, ...)"
INSERT INTO measurements (...) VALUES (?, ...), (?, ...), (?, ...), ...   -- 1000 Tupel
```

Ein einziges Statement statt 1000 — das spart Parsing- und Protokoll-Overhead auf der
DB-Seite erheblich.

## Was die Messung zeigt

| Stufe | Zeilen | Server ms | Zeilen/s | Faktor ggü. W3 |
|-------|--------|-----------|----------|----------------|
| W3 | 100000 | 10339 | 9 672 | — |
| **W4** | 100000 | 2664 | **37 541** | **≈ 3,9×** |

Gegenüber der Transaktions-Stufe [W2](W2.md) (498 Zeilen/s) ist W4 rund **75× schneller** —
allein durch bessere Insert-Technik, ohne Parallelität.

## Code-Walkthrough — die zweite Verbindung

`reWriteBatchedInserts` ist eine **Verbindungseigenschaft** und muss beim Aufbau der
Connection gesetzt sein; man kann sie nicht pro Statement umschalten. Damit W3 und W4
denselben Code, aber unterschiedliche Verbindungen nutzen, gibt es zwei `JdbcTemplate`s:

- `config/BatchDataSourceConfig.java`:
  - `jdbcTemplate` (`@Primary`) → Boots normale DataSource (ohne den Parameter) → W3.
  - `rewriteJdbcTemplate` → zweite Verbindung mit `reWriteBatchedInserts=true` → W4.
    Die zweite Verbindung wird **aus der primären DataSource abgeleitet** (gleiche
    URL/Zugangsdaten, nur um den Parameter ergänzt). So funktioniert sie unverändert auch
    in den Integrationstests, wo die DataSource per `@ServiceConnection` auf einen
    Testcontainer zeigt.
- `service/WriteService.java` → `w4JdbcBatchRewrite(...)` ruft dieselbe `batchInsert(...)`
  auf, nur mit dem `rewriteJdbcTemplate`.

> Bewusste Vereinfachung: Die zweite DataSource wird **nicht** als Spring-Bean exponiert,
> damit Boots JPA-/Flyway-Autokonfiguration (die eine eindeutige DataSource erwartet) nicht
> gestört wird.

## Fallstricke & Trade-offs

- `reWriteBatchedInserts` wirkt nur bei **einfachen** `INSERT ... VALUES`-Statements (kein
  `ON CONFLICT`-Sonderfall etc.). Für unseren Fall ideal.
- Sehr große umgeschriebene Statements können Grenzen für Parameteranzahl/Statementgröße
  treffen — die Chunk-Größe (1000) hält das im Rahmen.

## Ausblick

- **[W5](W5.md)** zeigt dieselbe Batch-Idee mit **Spring Batch** (chunk-orientiert,
  restartfähig) — wenn nicht nur roher Durchsatz, sondern auch Robustheit zählt.
