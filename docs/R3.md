# R3 — Server-seitiges Streaming (NDJSON)

> **Track:** Read · **Vorgänger:** [R2](R2.md) · **Nachfolger:** [R4](R4.md)

## Konzept

R0/R1 bauen die **komplette** Antwort im Speicher zusammen und senden sie erst, wenn sie
fertig ist. Zwei Nachteile: Der Speicher wächst mit der Datenmenge, und der Client sieht
**lange gar nichts** (hohe Time-To-First-Byte).

R3 **streamt**: Der Server liest die Zeilen über einen **DB-Cursor** blockweise und schreibt
jede Zeile sofort als **NDJSON** (ein JSON-Objekt pro Zeile) in den Ausgabestrom. So liegt
immer nur ein kleiner Block im Speicher, und das erste Byte erreicht den Client fast sofort.

Der Cursor entsteht durch drei Zutaten (PostgreSQL-JDBC):
`autoCommit = false` + `fetchSize > 0` + `TYPE_FORWARD_ONLY`.

## Was die Messung zeigt

100 000 Zeilen:

| Stufe | TTFB (erstes Byte) | Gesamtzeit |
|-------|--------------------|------------|
| R1 (buffered) | ~0,454 s | ~0,80 s |
| **R3 (streaming)** | **~0,043 s** | ~0,85 s |

Die **TTFB sinkt um ~10×** — der Client kann sofort anfangen zu verarbeiten/anzuzeigen,
während der Rest noch fließt. Die Gesamtzeit ist ähnlich; der Gewinn liegt in **Reaktivität
und konstantem Speicher**, nicht in weniger Bytes.

## Code-Walkthrough

- `service/ReadService.java` → `streamNdjson(OutputStream)`: öffnet eine Connection mit
  `autoCommit=false`, setzt `fetchSize=1000`, iteriert das `ResultSet` und schreibt je Zeile
  `objectMapper.writeValueAsBytes(dto)` + `\n`.
- `controller/ReadController.java` → `r3Stream()`: gibt eine `StreamingResponseBody` zurück
  (`produces = "application/x-ndjson"`), die Spring MVC streamend abarbeitet.
- Client (`stages.ts`, `r3Stage`): das Harness misst über den Stream-Reader die **TTFB**;
  die Zeilen werden per Zeilenumbruch gezählt.

> Hinweis: Weil die Antwort früh „committed" ist, kann der `ServerTimingFilter` seinen Header
> nicht mehr setzen — bei R3 zählt daher die clientseitige TTFB/Gesamtzeit.

## Fallstricke & Trade-offs

- **Transaktion offen halten:** Der Cursor lebt in einer offenen Transaktion, solange
  gestreamt wird. Bei sehr langsamen Clients bindet das eine DB-Verbindung.
- **Fehler mitten im Stream:** Ist der HTTP-Status (200) schon gesendet, kann man ihn nicht
  mehr ändern — Fehlerbehandlung während des Streamens ist kniffliger.
- NDJSON ist ideal fürs zeilenweise Verarbeiten; ein einzelnes großes JSON-Array wäre für
  Streaming unpraktisch (Klammern/Kommas).
